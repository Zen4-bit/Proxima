Agents

An agent is a seat — name + provider + route + model + effort + persona. Add the same provider more than once with different models or efforts (“Opus · max” and “Sonnet · low”, or “GPT high” and “GPT low”) to run a single-provider panel. Names become ids for @mentions and HANDOFFs (@opus-max).

Roster and library — the Agents tab is a table: one row per agent, every cell editable in place (name, provider, route, model, effort, tools, persona). + add agent… lists your library first, then a vendor to start a new seat from. Agents go into the library, and every new chat starts with all of them. The checkbox on each row decides who takes turns this time — untick to bench an agent without losing its setup; benched agents get no turns, no mentions and aren’t introduced to the others. Editing a library agent applies everywhere it is used. ✕ takes one row out of this chat, clear all empties the roster (library seats can be added back; anything not in the library was the only copy), and the library chips (📚) remove an agent for good. 🎨 colours tints each seat’s cards in the transcript so you can tell who said what at a glance. The tab strip collapses to a one-line summary.

Setups — setups… replaces the whole panel in one go — who is in it and how they talk (mode, rounds, brevity, context, independent rounds, judge). Four are shipped; save setup stores the current chat as one of your own and delete… removes yours. A shipped setup names only vendors, so models and efforts come from whatever is installed and logged in on this machine rather than from someone else’s.

Provider and route — Provider is the vendor — Claude, ChatGPT, Gemini, Perplexity, or an endpoint you registered. Route is how Proxima reaches it, and it is the only place that is decided: subscription · browser tab (the tab you are already signed in to), subscription · its CLI (Claude Code, Codex or Gemini CLI on this machine — the only route that can hold workspace tools), or API key, billed per token. Only routes this machine can actually take are listed: a CLI that is not installed is greyed out, and the API route appears only when API mode is on in Settings — selectable with a key for that vendor, listed but disabled without one. Keys and API mode are only ever set in Settings; ↻ re-reads them, re-probes the CLIs, and asks each key’s provider for its model list. Chats saved before this had a route called auto that followed Settings; those seats keep it, labelled follow Settings, until you choose a route for them.

Models — the list is grouped by where each entry came from. answered on this machine means a real turn has proved it; aliases the CLI lists / your account is what the CLI reports about itself; full ids · not tried here comes from a public catalogue and is a candidate list — a CLI may reject one. ▷ runs one short turn on the model right now, which is the only way to know, and a model that answers moves to the top group and stays there. custom… gives a free-text box, because Claude Code accepts full claude-… ids that no list here enumerates. On an API seat the list is what your key returns from /v1/models. A browser seat has no model picker at all — it answers on whatever its tab is set to, and Proxima does not drive that menu, so change it in the tab.

Local models — Settings → API → Local / custom endpoint registers any OpenAI-compatible server (Ollama, LM Studio, vLLM, llama.cpp, a gateway) under a name of your choice — give it the full …/v1/chat/completions URL. It then appears as a provider in the roster, API-only (no browser tab, no effort switch), with its model list pulled from the endpoint's /models; the model id is required. Such seats work whether or not API mode is on.

Workspace and tools — the Workspace tab attaches a git folder to the chat. CLI seats then get a Tools level: read (list / read / search files, to verify claims), write (edit files; shell limited to git status/diff/log) or full (edit + any shell command — no sandbox, so use a throwaway clone). Runs happen on the chat's own branch (multiai/…), cut fresh from your base branch — the one the folder is on, or main/master when it is parked on another chat's branch — never from another chat's changes; each writer turn is committed under the seat's name and appears in the transcript as a 🛠 change card with the diff, so every other participant — and you — can review it. One writer edits at a time; readers overlap. Uncommitted work on another branch blocks the run. Uncommitted work on the chat's own branch is swept into a commit by the next run, labelled as an interrupted turn — so once a run has left the folder on multiai/…, don't keep your own edits there. Merge or delete the branch when you're done.

Route differences — API and CLI turns are one-shot, so Delta context becomes Bounded for them (browser agents keep Delta). Stop kills CLI processes and aborts browser turns; an API call already in flight finishes and is discarded. Codex must support the chosen model on your account (gpt-5.5 does; gpt-5 does not on ChatGPT plans).

Classic mode

Discuss vs. Debate — Discuss has participants build on each other's points toward a shared answer. Debate assigns opposing sides and has them argue; with more than two participants each takes a distinct stance.

Rounds — how many times each participant speaks in turn. One round is usually enough for a quick comparison; use 2-4 for a discussion that needs to actually converge or a debate that needs rebuttals. More rounds costs more time and, if you're on metered API keys, more money.

Brevity — caps reply length. "max 4 sentences" keeps a multi-round discussion skimmable; switch to "as long as needed" for a single deep-dive round.

Context — what each participant is sent every turn. Bounded (default): the pinned State summary, a condensed digest of older messages, and the last N messages verbatim (Context window) — self-contained and stays small. Delta: only the messages since that AI's last turn; its own provider-side thread remembers the rest, and a rolling summary (refreshed every “Auto-summary every” messages, via the Judge provider) rides along as the topic block — the cheapest per turn; a fresh or rotated thread gets one full catch-up so nothing is lost. Full: the entire transcript every turn, the way the original ProximaChatApp worked — simplest, but it grows without limit and long chats will hit provider limits (that is what caused the HTTP 500s and timeouts late in long sessions).

Each chat gets its own provider-side thread per AI (rotated every 12 turns, or 40 in Delta mode), so chats never bleed into each other or into the MCP tools.

Stop token / PASS — participants are asked to begin a reply with the stop token (default DONE) when they think the group has converged, and to reply PASS when they have nothing new. With “Stop early when all agree” on, a round where everyone says the token or passes ends the run — no more rounds of “Agreed, nothing further”. Passes are shown dimmed and are not fed to the other AIs; neither are errors.

Directed turns — mention participants in your message to set this Send's order: @claude kick off, others review makes Claude speak first; only @gemini and @chatgpt restricts the round to those two. Use an agent's id (@opus-max), its name without spaces, or the provider when only one agent uses it. Naming an order overrides Independent rounds for round 1 — a blind round starts everyone at once, so there is no order in it to set — and the setting resumes from round 2. only is unaffected: it changes who takes part, not the order.

Independent rounds — a blind round runs every participant at once and shows none of them what the others are saying in that round — replies, passes and workspace diffs alike. Completed rounds stay visible, so round 2 answers round 1 and the discussion still happens, one round later. every round is the default: turn-taking makes a round asymmetric (the first seat answers you, the last answers five peers, and later seats converge on whoever spoke first), and one parallel batch per round makes a run about as slow as its slowest seat rather than the sum of them. first round only is the old behaviour — independent opening positions, then strict turn-taking. off restores turn-taking throughout. In Debate with three or more participants, stances are assigned (for / against / critical evaluator / third option) rather than left to chance.

Charter mode — turns the coworking charter's discipline into engine rules: participants must tag claims VERIFIED [who/how/path], UNVERIFIED or ASSUMED [basis] (agreement never upgrades a claim); plain agreement counts as PASS; every message ends with HANDOFF → <participant>: …, OPEN → … or COMPLETE → …; a HANDOFF pulls the named participant forward (next in this round, or first in the next); and one participant per round holds a rotating red-team seat (marked in the feed) whose job is the strongest objection to the emerging consensus. With Independent rounds on every round, a HANDOFF cannot pull a seat forward inside a round — everyone is already in flight — so it applies to the next round and the run says so once; set it to off if in-round handoffs matter more.

Judge — after a discussion, ask one provider to read the transcript and give a verdict. Judge scope: the whole chat, everything since your last message, or only the last round.

Summarize state — asks the Judge provider for a pinned summary (decisions, open questions, claims to verify, next step). It becomes the compaction point: later turns start from the summary instead of the older transcript. Use it whenever you'd otherwise ask “what is the state of the discussion”.

Personas — a shared library of a few built-ins (Skeptic, Optimist, Devil's Advocate, Pragmatist, Domain Expert, Concise Summarizer) plus any .md/.txt file you drop in the personas folder. Pick one on each agent's card in the Agents block; the same library also fills in a crew role's Instruction in Orchestrated mode, so you're not maintaining two systems.

Orchestrated mode

Crew — a fixed pipeline of roles (e.g. Researcher → Writer → Reviewer), each handing its output to the next. Edit roles, providers and instructions freely; pick providers whose strengths match the role (e.g. a search-grounded model for Researcher).

Workflow — your own ordered list of steps, one per line, as provider: task (provider is optional — omit it to use whichever is enabled first). Each step gets the previous step's output as input.

Loop — one provider generates, another reviews against the original task and either says CONVERGED or gives feedback; it keeps iterating up to Max turns. Good for "keep refining until it's actually right" tasks; pick a reviewer that's genuinely critical, not just agreeable.

Agent (file tools) — the only Orchestrated strategy that touches your actual filesystem. (Classic CLI seats with a Tools level touch it too, and are confined only by the Tools level you pick — see Workspace and tools above.) None of these providers have real API tool-calling wired up (they're browser chat, not tool-using APIs), so this is built as a loop: the model is told a small format for requesting a file operation, we execute it against the one folder you chose, and feed the result back for up to Max turns, until it replies with plain text instead of a tool request. That reply is the final answer. Reads, writes, and deletes all happen with no confirmation step — the only safety boundary is that it cannot reach anything outside the folder you pick. Point it at a scratch folder, not anything you'd mind losing.

Mode is locked once a chat has its first message, since Classic transcripts and Orchestrated pipeline runs don't mix well in one thread — start a new chat to switch.

General

Attachments (📎) fold text files into your prompt and note images/binaries by name only — none of these providers take image input through this tab.

Stop interrupts immediately: the reply in flight is aborted inside the provider's tab (so it stops occupying that provider's queue), queued turns are skipped, and nothing is shown or saved from it. In Delta mode the affected provider gets a fresh thread with a catch-up on its next turn.

New chats are titled from the first words of your first message (free, instant); ✨ next to the title asks the Judge provider for a better one. Rename any time via ✏.

Local agents — Codex, Claude Code or any script can join a chat through the gateway API on this app's REST port (Settings → API, default http://127.0.0.1:3210): GET /v1/multiai/chats, GET /v1/multiai/chats/<id>?since=<messageId>, POST /v1/multiai/chats/<id>/messages {"who":"Codex","provider":"codex","text":"…"} to append a turn, POST /v1/multiai/chats/<id>/run {"text":"…","rounds":1} to post a message and run a round, POST …/stop. Appended turns show up here live and are part of the transcript the browser AIs see. Claude Desktop, Claude Code, Codex and any other MCP client get the same through the proxima MCP server's multiai_* tools (list, read, post a message, run rounds, wait, stop) — no HTTP needed.

Runs belong to their chat, not to the screen: you can switch chats while one is running (● in the list), and its messages keep arriving and are saved. Each chat allows one run at a time. History is saved atomically with a rolling backup (multiai/chats.backup.json in the app's data folder); a damaged file is parked, never overwritten.

Message IDs & context — every message has a hidden unique id and a short label like 0103CG: cycle 01 (a cycle is one Send), round 03 (the turn within it), then a 2-letter agent code. Right-click any message, in the feed or the ledger, to add it as context for your next message (it's folded into the outgoing prompt and called out by label, even across chats) or to copy its reference label.

Click a ledger row to jump the transcript to that message. The ledger's two dropdowns filter by cycle·round and by agent.

Browser and API seats only see text you send them. CLI seats are different: a Claude Code, Codex or Gemini CLI seat with a Tools level reads and writes the workspace folder you attach, and at full it runs any shell command there. A Codex seat runs with its sandbox bypassed even at none, held back only by its system prompt. The 📎 attach button is a one-way bridge: it reads a local file client-side and folds its text into your prompt (images/binaries are noted by name only).

🔒 Security & Key Storage Architecture

Session Mode Security

Operates via local Chromium instances. Session cookies and login tokens are stored locally on your machine.

Credentials and tokens never leave your system. Direct encrypted connections are made to official AI provider domains.

API Key Encryption

All Bring Your Own Key (BYOK) secrets are encrypted on-disk using hardware-bound encryption (DPAPI) via the safeStorage API.

Once loaded, requests bypass browser views and communicate directly with raw endpoints, guaranteeing zero telemetry and privacy.

💡 Why Proxima Exists ▸

In late 2025, I hit a massive roadblock with AI coding tools. Due to outdated training data, coding models would frequently hallucinate, guess wrong solutions, and end up ruining the source code and overall code quality. To fix this, I tried setting up local agents using Model Context Protocol (MCP) APIs, but the results were highly disappointing. The API responses were low-quality and frustratingly inaccurate, all while draining money for every single API call.

That’s when a wild idea struck: What if we could turn actual Web Models—like ChatGPT, Gemini, Claude, and Perplexity—into local MCP servers? By tapping directly into web interfaces via free logged-in accounts, I could give my local agents access to high-quality, up-to-date reasoning without paying for expensive and subpar API keys.

Proxima was born as a purely personal utility. I used it heavily for months to streamline my own work, with absolutely no plans of open-sourcing it. However, seeing so many developers online struggling with the exact same API costs and low-quality hallucinations, I decided to share it with the world. Proxima exists to empower developers with absolute privacy, speed, and high-quality local workflows—without forcing anyone to buy expensive software or pay for unreliable API keys.
